# 美味助手 · 称号成长系统产品规格

## 1. 产品定位

称号系统不应独立成为“签到小游戏”，而应嵌入真实做饭闭环：

```text
选择菜谱 → 互动分工 → 进入烹饪 → 完成菜谱 → 记录行为 → 结算称号
```

两套称号承担不同职责：

- **主线称号**：按已完成菜谱数量自动升级，负责长期成长感。
- **隐藏称号**：按特殊行为解锁，负责惊喜、探索和故事感。

推荐把“等级”与“展示称号”分开：

```text
等级称号：精良 · 香气捕手（系统自动计算，不能降级）
展示称号：烟火初燃（用户从已解锁隐藏称号中选择）
```

这样既不会让隐藏称号覆盖主线进度，也允许用户表达个性。

---

## 2. App 信息架构

### 我的

首屏展示：

1. 当前主线品质与称号。
2. 已完成菜谱数量。
3. 距离下一级还差多少道菜。
4. 连续做饭天数。
5. 已解锁隐藏称号数量。
6. 当前装备的展示称号。

### 称号殿堂

分为两个区块：

- **主线称号**：当前等级上下各展示 1–3 个节点，不一次性向新用户铺开全部 25 级。
- **隐藏称号**：已解锁显示完整名称，未解锁只显示「？？？」与线索。

### 菜谱完成页

用户完成最后一个烹饪步骤后，出现明确的“完成这道菜”确认。确认后：

1. 写入完成记录。
2. 更新主线数量。
3. 执行隐藏条件检测。
4. 将本次新解锁结果进入弹窗队列。

仅浏览详情、收藏或进入烹饪模式，不计为完成。

## 3. 与饭局游戏联动

### 食谱骰子

- 第一次成功产生随机菜谱：解锁「命运开锅」。
- 使用 10 次：解锁「天选掌勺人」。
- 连续 3 次命中同类菜：解锁「欧皇厨师」。
- 用户明确点“不想吃，再摇一次”累计 10 次：解锁「选择困难大师」。
- 随机推荐菜真正完成 100 道：解锁「命运料理大师」。

必须区分三个事件：

```text
dice_rolled             骰子完成一次有效落地
dice_recipe_rejected    用户明确拒绝结果并重摇
recipe_completed        用户完成随机产生的菜谱
```

不能用“点击骰子”替代“有效落地”，否则快速连点会污染数据。

### 谁做饭、谁洗碗

首版只负责饭局分工，不额外派生称号，避免奖励系统膨胀。需要保留以下事件，以便未来加入公平分工、家庭协作类称号：

```text
party_created
party_participant_added
kitchen_roles_assigned
assigned_role_completed
```

## 4. 品质视觉规则

| 品质 | 主色 | 使用位置 | 动效强度 |
|---|---|---|---|
| 普通 | 浅银 `#D8D8D4` | 标签、边框 | 无持续动效 |
| 精良 | 蓝 `#72A9FF` | 标签、进度高光 | 轻微光点 |
| 稀有 | 紫 `#B987FF` | 卡片描边、徽章 | 一次性扫光 |
| 史诗 | 橙金 `#F3A35D` | 徽章、解锁弹窗 | 粒子与触觉反馈 |
| 传说 | 红金 `#FF6D55` + `#E4B45B` | 渐变徽章 | 短暂金色流光 |
| 神话 | 彩金 | 徽章与背景纹理 | 极慢渐变，不持续闪烁 |
| 至尊 | 黑金 `#171714` + `#F3C86B` | 专属卡片 | 强一次性揭晓，静态陈列 |

颜色不是唯一识别方式。每个品质还应同时使用：

- 不同徽章轮廓。
- 品质名称文字。
- 不同边框或纹理。
- VoiceOver 可读的品质描述。

避免高频呼吸、闪烁和无限粒子；“高级感”来自材质、留白和短促仪式感。

## 5. 解锁弹窗规则

### 主线升级

```text
称号升级

恭喜你完成第 8 道菜，晋升为：
精良 · 香气捕手

再完成 2 道菜，即可解锁：
精良 · 家常料理师
```

操作：

- 继续
- 查看称号

### 隐藏称号

```text
隐藏称号解锁

命运开锅

第一次用骰子随机出菜，今晚由命运替你开锅。
```

操作：

- 收下称号
- 设为展示称号（可在称号殿堂中再次修改）

### 同时解锁多个称号

一次完成行为可能同时触发主线升级、连续天数、菜系数量和特殊数字。不得连续弹出 4–5 个全屏弹窗。

推荐优先级：

```text
至尊/神话主线 > 特殊数字 > 稀有隐藏 > 普通主线 > 常规隐藏
```

一次行为最多显示 1 个完整弹窗，其余合并为：

```text
另外解锁 2 个称号
```

点击进入结算页统一查看。

## 6. 关键数据模型

```json
{
  "userId": "user_001",
  "recipeCompletionCount": 8,
  "currentMainTitleId": "main_005",
  "displayHiddenTitleId": "hidden_streak_003",
  "unlockedTitleIds": [
    "main_001",
    "main_002",
    "main_003",
    "main_004",
    "main_005",
    "hidden_streak_003",
    "hidden_random_001"
  ],
  "cookingStreakDays": 3,
  "lastCompletionAt": "2026-06-20T19:28:00+08:00"
}
```

称号定义与用户进度分离。称号文案、阈值和颜色可以远程配置，但已发放的称号不能因配置更新而被撤回。

## 7. 事件结构

统一事件建议：

```json
{
  "eventId": "evt_uuid",
  "eventName": "recipe_completed",
  "userId": "user_001",
  "occurredAt": "2026-06-20T19:28:00+08:00",
  "timezone": "Asia/Shanghai",
  "recipeId": "mapo-tofu",
  "recipeTags": ["spicy", "meat"],
  "cuisine": "sichuan",
  "source": "dice",
  "localHour": 19,
  "isWeekend": true,
  "photoUploaded": true,
  "cookedForOthers": true
}
```

服务端按 `eventId` 幂等处理，防止网络重试导致完成数重复增加。

## 8. 实现注意事项

### 连续做饭

- 按用户本地时区的自然日计算。
- 同一天完成多道菜只增加一次连续天数。
- 跨时区旅行时保留事件原始时区，避免重复或断档。

### 时间与节日

- 深夜、清晨、周末按事件发生地本地时间计算。
- 春节、端午、中秋需要农历映射，不能只写固定公历日期。
- 生日称号依赖用户主动填写生日，默认不采集。

### “连续不点外卖”

普通 iOS App 无法可靠读取用户是否点过外卖。只能采用：

- 用户自报与每日确认；或
- 用户主动连接有能力提供订单数据的外部服务。

没有可靠数据源时，不应自动声称用户“连续未点外卖”。`title-catalog.json` 已将此类规则标记为 `selfReportedOrExternalIntegration`。

### 点赞与社交

“被点赞”类称号需要社区、分享落地页和服务端账号体系。首版没有社交后端时，应隐藏该分类，而不是显示永远无法完成的任务。

### 极高里程碑

5000 道菜如果每天完成一道，需要约 13.7 年。可以保留为终身至尊目标，但前台只展示当前等级附近节点；不要让新用户首屏看到 5000 造成挫败感。

### 特殊数字

520、666、888、999、1000、1314、2026 是“精确命中”称号。升级过程中必须在每次完成事件后判断，而不能仅判断当前总数是否大于阈值。

## 9. MVP 建议

第一版先上线 20–25 个真正可追踪的称号：

- 全部早期主线称号（1–100 道）。
- 连续 3 / 7 / 30 天。
- 深夜第一次、清晨 5 次。
- 菜品分类 10 道。
- 同一道菜 3 次。
- 骰子 1 / 10 次。
- 每日推荐第一次、连续接受 7 天。
- 成品图 20 次。
- 投喂第一次、10 次。

后续再开放社交、外卖、节日和千道以上称号。这样首版数据可信、触发清晰，也便于验证称号系统是否真的提升完成率与留存。
